Hermes Agent · security and operations reference

Secure Hermes Installation

This plan defines the dedicated Fedora Server 44 appliance boundary for Hermes Agent. The executable contract lives in the Fedora Server guide and the deployment handoff.

Security boundary

Hermes runs as a locked, dedicated hermes account inside a rootless Podman container. A root-owned Quadlet and systemd drop-ins own the service definition; the only persistent mount is /home/hermes/data to /opt/data with a shared SELinux label.

  • Fedora Server 44 x86_64 with LUKS-backed storage, UEFI Secure Boot, enforcing SELinux, and firewalld.
  • SSH is the only permitted non-loopback host service; Cockpit, discovery, printing, and sleep paths are disabled.
  • The image is pinned to the checked-in digest and the Quadlet uses Pull=never.
  • The container has no host home, device, Podman socket, published port, or injected credential mount.
  • Hermes approvals remain manual and its write boundary is limited to the persistent data directory.

Promotion before production

  1. Verify the locally supplied Fedora Server DVD against Fedora's signed checksum and expected SHA-256.
  2. Create lab-hermes-server with 8 GiB RAM, 2 vCPUs, a 40 GiB encrypted disk, Secure Boot, and 172.16.99.12.
  3. Run the offline test suite and the complete Fedora Server deployment in the disposable VM.
  4. Complete exactly one selected provider flow, configure its model, and require the exact HERMES_OK response.
  5. Revoke all supported provider credentials, purge fresh Hermes data, remove fixture privilege, and destroy the VM.
  6. Only after destruction verification, issue the secret-free promotion record.
Production gate: production deploy and configure-provider require a matching promotion record. A record is bound to the first production host's machine-id hash and SSH ED25519 fingerprint. A failed deployment may resume on that host with unchanged inputs; another host is rejected.

API keys are entered only through Hermes' interactive prompt. They are never command-line arguments, shell input supplied by the controller, logs, local deployment state, or promotion records. Switching provider or model requires a new VM certification record; failed switching restores the previously accepted configuration.

Host updates and rollback

The host module owns the Fedora Server package contract and uses DNF5 offline transactions. Automatic updates download packages only with apply_updates=False and reboot=never. The controller stages an offline upgrade, records the boot ID, performs the planned reboot, and verifies the new boot ID and offline transaction log before continuing.

Rollback restores Hermes data and manifest-tracked host configuration. It does not claim to reverse RPM or kernel updates; a host replacement is handled through console-verified adopt-host and a fresh promotion binding.

Operator sequence

HERMES_REPO=${HERMES_REPO:-$HOME/code/repos/DS-Workspace/hermes-fedora-host}
HERMES_MEDIA_DIR=${HERMES_MEDIA_DIR:-$HOME/Downloads/fedora-server-44-1.7}
HERMES_SSH_IDENTITY=${HERMES_SSH_IDENTITY:?export the verified SSH private key path}
cd "$HERMES_REPO"

./hermes-certify-vm.sh \
  --iso "$HERMES_MEDIA_DIR/Fedora-Server-dvd-x86_64-44-1.7.iso" \
  --checksum "$HERMES_MEDIA_DIR/Fedora-Server-44-1.7-x86_64-CHECKSUM" \
  --fedora-keyring "$HERMES_MEDIA_DIR/fedora.gpg" \
  --identity-file "$HERMES_SSH_IDENTITY" \
  --provider openai-codex \
  --model gpt-5.6-luna

Then verify the reinstalled host fingerprint at the local console, run adopt-host, run the read-only check, and execute deploy with the printed absolute --promotion-record. OAuth/API-key entry and the final authenticated response are deliberate operator gates.
