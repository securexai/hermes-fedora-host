Security-first deployment plan

Secure Hermes Installation

A staged plan for running Hermes Agent on Fedora Kinoite 44 using a dedicated unprivileged account, rootless Podman, and a hardened systemd Quadlet.

Prepared: 21 August 2026 Target: Fedora Kinoite 44 Status: Executed 21–22 August; live-audited 23 August 2026

Executive summary

The recommended deployment wraps the entire Hermes process inside a rootless container owned by a separate hermes operating-system user. It begins with no host project mounts, no container-engine socket, no public ports, no third-party extensions, and only revocable, low-privilege credentials.

Post-install audit result. The initial 23 August audit found the hardened Quadlet inactive while a manual setup/CLI container was running without the planned controls. The host was subsequently updated and cut over to the digest-pinned production service; the container boundary and fail-closed Hermes policy passed live acceptance. See the tested installation guide for the as-built evidence and remaining host exceptions.

Boundary

Whole-process OS isolation, not terminal-command filtering alone.

Supply chain

Named release, tested and scanned, then pinned by complete digest.

Exposure

No inbound ports by default; loopback-only if a local API is required.

Fedora Kinoite 44 ├── Normal user │ └── Personal files and credentials — never mounted into Hermes └── Dedicated hermes user ├── No sudo, SSH login, or privileged groups └── Rootless Podman + user systemd └── Hermes whole-process container ├── One private /opt/data mount ├── No Podman/Docker socket ├── No host namespaces or devices └── No published ports by default

Version clarification. No official “Hermes Agent 2.0” release was found. As of this plan’s date, the official latest release is v0.20.5, tagged v2026.8.19. The release will be checked again immediately before installation.

VM escalation rule. Use a dedicated KVM/libvirt virtual machine when Hermes will ingest highly untrusted content while holding powerful cloud, production GitHub, Kubernetes, email, or infrastructure credentials. Rootless containers still share the host kernel.

Objectives and non-goals

Security objectives

  • Prevent Hermes from reaching the normal user’s files and credentials.
  • Confine terminal, file, code-execution, MCP, plugin, hook, and skill paths.
  • Minimize host privileges, mounts, devices, network exposure, and persistence.
  • Make image selection, configuration changes, updates, and rollback auditable.
  • Use credentials that are narrow, capped, monitored, and easy to revoke.

Initial non-goals

  • Public API or dashboard hosting.
  • Desktop automation or access to Wayland, X11, D-Bus, audio, or cameras.
  • Access to the normal user’s repositories, SSH agent, browser, or home directory.
  • Unreviewed community skills, plugins, hooks, MCP servers, or autonomous cron jobs.
  • Production-grade cloud or infrastructure administration.

Implementation plan

Phase 0Fix the security profile

Record the intended use before any installation:

  • One operator only.
  • Interactive CLI or a private messaging gateway.
  • No arbitrary public callers.
  • No high-value cloud, infrastructure, personal email, or password-manager credentials.
  • Web, browser, cron, MCP, plugins, and community skills disabled initially.
  • No API or dashboard port unless there is a specific requirement.
Exit gate

The required features and credential classes are documented, and the container-versus-VM decision is explicit.

Phase 1Verify and harden the Kinoite host

Run a read-only preflight, then apply normal host updates separately:

  • Confirm Fedora/Kinoite release, CPU architecture, and pending deployments.
  • Confirm Secure Boot status where applicable.
  • Verify SELinux is enforcing and firewalld is active.
  • Verify Podman, Quadlet, cgroup v2, rootless networking, and local container storage.
  • Verify the normal home directory and sensitive subdirectories deny unrelated users.
  • Capture a concise pre-install inventory for later comparison.

The Hermes host installer script will not be executed. The supported container image is the deployment artifact.

Exit gate

The host is current, SELinux remains enforcing, and rootless Podman passes a minimal smoke test.

Phase 2Create the dedicated OS identity

Create an unprivileged hermes user with:

  • A private home directory with mode 0700.
  • A locked password and no SSH authorized keys.
  • No membership in wheel, docker, libvirt, or other privileged groups.
  • Dedicated subordinate UID and GID ranges for rootless Podman.
  • User-systemd lingering so the rootless service can start at boot.

Install the Quadlet definition as a root-owned file beneath /etc/containers/systemd/users/<uid>/. This keeps the service declaration outside Hermes’ writable state while preserving a rootless runtime.

Exit gate

The account cannot use sudo or read the normal user’s synthetic canary files, and rootless Podman works under that identity.

Phase 3Establish the supply-chain gate

  1. Select a named release tag; do not use latest or main.
  2. Cross-check it between the official GitHub releases and docker.io/nousresearch/hermes-agent.
  3. Pull the fully qualified image as the hermes user.
  4. Record the complete platform digest.
  5. Inspect architecture, entrypoint, configured user, labels, layers, and creation time.
  6. Run a vulnerability scan using an ephemeral scanner container.
  7. Smoke-test the image without credentials.
  8. Pin the production Quadlet to docker.io/nousresearch/hermes-agent@sha256:….
  9. Set Pull=never so production updates remain explicit.

Digest pinning guarantees that the selected bytes do not drift; it does not independently prove publisher identity. If registry signatures or attestations remain unavailable, record that residual risk or build locally from a verified release tag.

Exit gate

A specific digest has passed inspection, scanning, and a credential-free smoke test.

Phase 4Prepare persistence and secrets

  • Create one host data directory, owned by hermes and mode 0700.
  • Mount it as /opt/data with a private SELinux label such as :Z.
  • Set the generated .env file to mode 0600.
  • Put no secret values in Quadlet, deployment scripts, shell history, Git, or process arguments.
  • Use separate provider and messaging credentials created for Hermes.
  • Apply provider spending limits, narrow scopes, alerts, and revocation procedures.
  • Back up the data directory only into encrypted storage.
  • Never attach two Hermes gateway containers to the same data directory.

Do not mount the normal home directory, SSH material, cloud config, browser state, D-Bus, display sockets, host devices, or the Podman/Docker socket.

Exit gate

The mount list contains exactly the intended private data directory, and the backup destination is encrypted.

Phase 5Run controlled first-time setup

Run setup interactively in a temporary container using the pinned image, dedicated account, and private data mount. Publish no ports and pass no extra host paths or sockets.

Review the generated configuration before starting a gateway:

  • Use the local terminal backend inside the outer container; it is local to the container, not the Kinoite host.
  • Keep dangerous-command approvals enabled.
  • Set cron and unattended one-shot approvals to deny.
  • Enable tool-loop hard stops and fail-closed security scanning where supported.
  • Disable unneeded package installers, web tools, browser automation, MCP, plugins, hooks, cron, and messaging adapters.
  • Review executable code—not only metadata—before installing any third-party extension.
  • Configure explicit caller allowlists before enabling a messaging adapter.
  • Never enable a global “allow all users” setting.
Exit gate

The configuration has been manually reviewed, unused surfaces are disabled, and only low-privilege credentials are present.

Phase 6Build the hardened Quadlet

The root-owned production definition will include:

  • Pinned image digest with Pull=never.
  • The single private /opt/data mount.
  • Default Podman seccomp and SELinux confinement.
  • NoNewPrivileges=true.
  • All capabilities dropped, then only the image’s tested s6 startup requirements added back.
  • No privileged mode, devices, host networking, or shared host namespaces.
  • No container-engine socket.
  • A read-only root filesystem if compatibility tests pass.
  • Explicit, size-limited tmpfs mounts for runtime temporary paths.
  • A restrictive umask.
  • Initial limits of approximately 4 GiB memory, two CPUs, and a bounded PID count.
  • Controlled restart-on-failure behavior and a non-network health check.
  • Journald logging plus bounded persistent Hermes logs.

Do not blindly force the internal container user. The supported image initializes through s6 as container root, performs limited setup, and then drops supervised services to its internal hermes user. Rootless Podman maps that container root into the dedicated host user namespace.

Exit gate

The service starts with the minimal tested capability set, passes health checks, and retains SELinux confinement.

Phase 7Control inbound and outbound networking

Inbound

  • Publish no ports when an outbound messaging adapter is sufficient.
  • If a local API or dashboard is required, bind explicitly to 127.0.0.1.
  • Require a strong API key and exact CORS origins; never use *.
  • Use an SSH tunnel or authenticated VPN for remote access.
  • Never use host networking for convenience.

Outbound

  • Initially permit only setup and the selected provider’s required traffic.
  • Block loopback, private, link-local, cloud-metadata, and LAN destinations at a network boundary where practical.
  • For stricter control, place Hermes on an internal Podman network and route required traffic through an independently controlled allowlisting proxy.
  • If arbitrary web access is required, use a separate low-trust instance without valuable credentials or move it into a VM.
Exit gate

Only intended endpoints are reachable, and no service is exposed beyond its approved interface.

Phase 8Validate the security boundary

  • The container cannot enumerate or read the normal user’s home.
  • Container inspection shows only the approved data mount.
  • No Podman or Docker socket exists inside the container.
  • No unexpected device or host namespace is shared.
  • The effective capability set matches the approved minimum.
  • SELinux remains enforcing without broad exemptions.
  • No externally reachable listening port exists.
  • Loopback-only services reject non-loopback access.
  • Unauthenticated API calls and unauthorized messaging identities are denied.
  • Provider access works using only the intended low-privilege credential.
  • Private-network and metadata destinations are blocked under the chosen egress policy.
  • Memory and PID limits behave as expected.
  • The rootless service starts correctly after a reboot.
  • An encrypted backup-and-restore drill succeeds.

Use synthetic canary files for isolation testing. Do not test by attempting to expose real credentials.

Exit gate

Every checklist item has recorded evidence or an explicitly accepted exception.

Phase 9Establish update and rollback

Automatic image updates remain disabled. For each upgrade:

  1. Review the official release notes.
  2. Pull the new named tag separately.
  3. Record and scan its digest.
  4. Run a credential-free smoke test.
  5. Stop Hermes.
  6. Create an encrypted point-in-time backup of /opt/data.
  7. Change the root-owned Quadlet to the new digest.
  8. Reload, start, and run functional and isolation checks.
  9. Retain the prior digest and backup until the release is proven stable.

Back up before first boot because a new image can migrate persisted configuration. Rollback restores both the prior image digest and the pre-migration data snapshot.

Exit gate

The rollback procedure has been tested, not merely documented.

Phase 10Operate and review

  • Review releases and security advisories weekly; update manually.
  • Review gateway authorization and runtime logs.
  • Audit skills, MCP servers, plugins, hooks, and cron jobs monthly.
  • Rotate provider and bot credentials regularly and immediately after suspicion.
  • Monitor provider spending and alerts.
  • Test backup restoration quarterly.
  • Keep the dedicated account free of unrelated files and services.
  • Maintain a secret-free deployment record containing tag, digest, configuration checksum, enabled surfaces, verification date, and rollback digest.

Deployment decision matrix

Use case Recommended boundary Credential posture
Interactive personal use with low-value provider key Kinoite + dedicated user + rootless Podman Separate key, spend cap, no production scopes
Private messaging gateway with explicit allowlist Same container boundary, no inbound host port Separate bot token and provider key
Broad web research or untrusted attachments Restricted egress or separate low-trust instance No infrastructure credentials
Cloud, Kubernetes, production GitHub, or personal email Dedicated KVM/libvirt VM plus rootless Podman Short-lived, narrowly scoped credentials
Public multi-user service Outside this baseline plan; requires a separate service design Per-tenant isolation and independent authorization

Verified findings

Finding Confidence
Hermes identifies OS-level isolation—not approval prompts or pattern scanners—as its security boundary and distinguishes terminal-only from whole-process isolation. Verified

Rootless Podman uses subordinate UID/GID mappings and separates container management by host user. Verified

Unresolved items and execution-time gates

  • Resolved Podman was upgraded from 5.8.1 to Fedora's 5.8.4 build. The administrator-owned Quadlet is placed directly; the affected pre-5.8.6 podman quadlet install --replace path is prohibited until Fedora supplies 5.8.6 or later.
  • Unknown The intended meaning of “Hermes Agent 2.0”; no matching official release was located.
  • Recheck Whether the selected container tag has registry signatures, attestations, or an SBOM at installation time.
  • Resolved The manual container was removed; only hermes.service now runs the digest-pinned gateway with a root-owned Quadlet and root-owned systemd user-unit drop-in.
  • Manual control Secure Boot remains disabled and must be enabled in firmware or accepted as a documented residual host risk.
  • Decision The 23 August scan found 18 unfixed CRITICAL and 275 unfixed HIGH findings; prefer a remediated image or record a narrow, time-bounded risk acceptance.
  • Decision Whether arbitrary web access, messaging adapters, local inference, or a local dashboard is actually required.
  • Decision Whether restricted egress justifies an independently managed allowlisting proxy.
